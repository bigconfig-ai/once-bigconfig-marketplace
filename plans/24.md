# Plan 24 — Multi-language package implementations

## Goal

Represent a BigConfig package as a single GitHub repository that can expose one or more language implementations, where each implementation lives on a branch in that repository and the branch name does **not** have to match the language slug.

Supported package languages for this change:

- TypeScript
- Python
- Clojure

The marketplace should store this implementation metadata, show it on package cards/details, and let users filter `/packages` by language.

## Current state reviewed

- `pocketbase/pb_migrations/1714000000_init_packages.js`
  - `packages` currently models one GitHub repo only: `github_url`, derived `name`, repo metadata, `tags`, `status`, etc.
  - There is no language/branch implementation field.
- `pocketbase/pb_hooks/packages.pb.js` and `pocketbase/pb_hooks/utils.js`
  - create hook derives `name` from `github_url` and protects repo/admin metadata on update.
  - New operational fields will need validation and protected-field policy decisions.
- `web/src/lib/pb.ts`
  - `PackageRecord` has no language fields.
- `web/src/components/PackageCard.astro`
  - card currently shows repo owner/name, submitter, stars, description, and tags only.
- `web/src/pages/packages.astro`
  - package list currently filters by search query plus tag groups only.
- `web/src/pages/packages/[owner]/[repo].astro`
  - copy prompt currently assumes users choose a language and run `bc-pkg owner/repo@<language>`, which will be wrong when branch names are arbitrary.
- `web/src/pages/submit.astro`, `web/src/pages/me/edit.astro`, `web/src/pages/me/packages.astro`
  - package submission/edit/dashboard flows currently have no way to provide or display language branch mappings.

## Recommended data model

Add two fields to the `packages` collection:

1. `language_branches` — JSON object, source of truth for implementation branches.

   Example:

   ```json
   {
     "typescript": "main",
     "python": "python-sdk",
     "clojure": "bb-clj"
   }
   ```

2. `languages` — multi-select field derived from the JSON keys, used for simple display/filtering and future PocketBase queries.

   Values:

   - `typescript`
   - `python`
   - `clojure`

Rationale:

- The JSON object captures the required language → arbitrary branch mapping.
- The multi-select field keeps language filtering simple and schema-visible.
- Hooks can normalize `language_branches`, deduplicate keys, validate allowed languages, and force `languages` to match the JSON keys so the duplicated data does not drift.

## Decisions

- Use the recommended `language_branches` JSON source of truth plus derived `languages` multi-select field.
- Every selected language must have an explicit branch name; no implicit default-branch fallback.
- PocketBase hooks must verify each configured branch exists on GitHub before accepting create/update.
- Existing package records will be manually backfilled; do not assume default language/branch mappings.
- Submitters can edit language/branch mappings after submission.
- Package cards should show language plus branch, e.g. `TypeScript @ main`.

## Proposed implementation

### 1. PocketBase schema migration

Create a new migration that updates the `packages` collection:

- add `language_branches` as a JSON field
- add `languages` as a multi-select field with values `typescript`, `python`, `clojure`, max 3
- add an index on `languages` only if PocketBase supports useful select indexes for this version; otherwise client-side filtering is enough for now
- do not auto-assume defaults for existing package records; manually backfill known language/branch mappings after migration

### 2. Hook validation and normalization

Update `pb_hooks/utils.js` with package language helpers:

- central allowed-language list and display labels
- `normalizeLanguageBranches(value)`
  - accepts an object only
  - trims branch names
  - rejects unknown language keys
  - rejects blank branch names
  - rejects duplicate/unsafe branch names if needed
  - returns `{ languageBranches, languages }`
- `validateGithubBranches(repoName, languageBranches)`
  - checks each branch exists in the submitted GitHub repo via GitHub API
  - is required on create and on language/branch updates
  - should use `GITHUB_TOKEN` if available, matching the existing metadata fetch pattern

Update `pb_hooks/packages.pb.js`:

- on create, validate `language_branches`, verify each configured branch exists, set normalized `language_branches`, and set derived `languages`
- on update, allow submitters to change `language_branches`; normalize, verify each configured branch exists, and update derived `languages`
- do not add `language_branches` or `languages` to protected fields; keep `languages` hook-derived so client-submitted values cannot drift from the JSON mapping

### 3. Shared frontend language constants/types

Add a small frontend helper, likely `web/src/lib/languages.ts`:

- language options with slugs and labels
- `languageLabel(slug)`
- `packageLanguages(pkg)` / `packageLanguageBranches(pkg)` helpers that tolerate older records without language data

Update `web/src/lib/pb.ts`:

- add `languages: string[]`
- add `language_branches: Record<string, string>`
- add user-facing field labels for PocketBase validation errors

### 4. Package submission/edit flows

Update package form pages:

- `web/src/pages/submit.astro`
  - add a “Languages” section
  - each supported language has a checkbox and a branch input
  - require at least one selected language
  - require a branch value for each selected language
  - submit `language_branches` as an object; let hooks derive `languages`
- `web/src/pages/me/edit.astro`
  - display/edit the same fields because submitters can modify implementation mappings after submission
  - require at least one selected language and an explicit branch value for each selected language
- `web/src/pages/me/packages.astro`
  - show language chips/branches in the user dashboard cards

### 5. Package card and detail display

Update `web/src/components/PackageCard.astro`:

- show supported languages prominently, separate from tags
- proposed compact card format: `TypeScript @ main`, `Python @ python-sdk`, etc.
- keep tags below the description as today

Update `web/src/pages/packages/[owner]/[repo].astro`:

- show an “Implementations” section with language → branch mappings
- update the copy prompt to list available implementations and use the selected branch, not the language slug:

  ```text
  - installer can be npx or uvx, ask me which one to use
  - choose one implementation:
    - TypeScript: main
    - Python: python-sdk
  - run <installer> bc-pkg owner/repo@<chosen-branch> package validate
  - iterate on failure
  ```

### 6. `/packages` language filter

Update `web/src/pages/packages.astro`:

- add a top-level filter group labeled `Languages`
- language buttons are based on the new language constants, not `TAG_GROUPS`
- cards get `data-languages="typescript,python"` from `p.languages` or the keys in `p.language_branches`
- keep tag filtering separate from language filtering
- recommended semantics:
  - selected tags: package must match all selected tags, preserving current behavior
  - selected languages: package may match any selected language
  - search query still matches name/description

### 7. Build verification

Run:

```sh
cd web && npm run build
```

If a PocketBase binary is available locally, also smoke-test package create/update in dev.

## Acceptance criteria

- Package records can represent one or more implementations in TypeScript/Python/Clojure with arbitrary branch names.
- New package submissions include at least one language branch mapping with an explicit branch for every selected language.
- Package create/update rejects unknown languages, blank branches, and branches that do not exist on GitHub.
- Submitters can edit language/branch mappings after submission, with the same validation.
- The package list has a `Languages` filter that works independently from tag filters.
- Package cards show supported language implementation metadata as language plus branch.
- Package detail pages and copy prompts use the configured branch names rather than assuming branch equals language.
- Existing packages without language metadata do not break static builds or page rendering while they await manual backfill.
- `cd web && npm run build` passes.

## Resolved questions

- Data model: `language_branches` JSON object plus derived `languages` select.
- Branches: always explicit; no default-branch fallback.
- GitHub validation: verify configured branches exist before accepting create/update.
- Existing packages: manually backfill language/branch mappings.
- Editing: submitters can edit language/branch mappings after submission.
- Card display: show language plus branch, e.g. `TypeScript @ main`.

## Non-goals

- Do not change the `applications` collection or ONCE application submission flow.
- Do not change launcher behavior in this plan.
- Do not convert package languages into generic tags; languages should be first-class package implementation metadata.
